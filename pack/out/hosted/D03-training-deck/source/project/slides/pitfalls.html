Ten mistakes early adopters keep making, each with the countermeasure that prevents it

01

SBOM built from the manifest

Generate it from the shipped artefact; add binary scanning

02

Scanner hits treated as active exploitation

Reachability first, VEX recorded; Art 14 needs real evidence

03

Default credentials shipped for convenience

Per-unit secrets; force credential set-up at first use

04

Debug ports left open on production units

Lock JTAG, SWD and UART; prove it with a debugger attach

05

Telemetry on by default “for product improvement”

Inventory data, make it opt-in, record the 2(g) justification

06

A logging opt-out that kills security events

Document which events persist, and why, in Annex II

07

Signed updates without anti-rollback

Monotonic counter; only authorised, audited downgrades

08

Security fixes bundled into feature releases

Maintenance branches with a security-only channel

09

Evidence assembled by hand when someone asks

Emit gate records, hashes and test results from CI

10

Our backend left out because “it is cloud”

Apply the three-element test; assess both ends of each link

Source: Application guide s. 14; Commission FAQ v1.4; BSI TR-03183-2; vendor material (Finite State, OmniTrust), unverified

Illustrative · 21

Ten mistakes early adopters keep making, each with its countermeasure. Read the bold line as “don’t” and the line beneath as “do”. Scanner hits are not active exploitation: apply reachability, record VEX, and keep Article 14 for reliable evidence that someone has exploited the flaw. Signed updates without anti-rollback let an attacker reinstall an old, vulnerable version. Evidence assembled by hand when an authority asks is the failure that hurts most; early adopters report that security is often fine but the decision trail cannot be shown. And our own backend is in scope even though it runs in the cloud. Three more from the implementation guide are not on the slide: vulnerability data inside the SBOM, no per-version support declaration for software, and a third-party service such as the weather API mistakenly assessed as our own backend. Ask each team to pick the two that apply most to them.
